# سیمرغ‌کارا / سیمرغ‌لجر

پلتفرم **SaaS چندمستأجری و پنل‌محور** برای مدیریت شرکت‌ها: سازمان و کارتابل،
منابع انسانی، مالی (سیمرغ لجر)، انبار، HRC (سلامت و ایمنی) و درگاه API.

```
سوپرادمین (سیمرغ)            ← /admin
  ├─ ساخت هولدینگ + تعیین «پنل‌های مجاز» و سقف شرکت‌های آن
  └─ ساخت شرکت + تعیین پلن، سقف کاربر و **پنل‌های فعال**
       │
       ▼
هولدینگ                      ← /holding
  └─ ساخت شرکت‌های خودش و **روشن/خاموش کردن پنل هر شرکت** (در سقف مجوز هولدینگ)
       │
       ▼
شرکت (Tenant)  ← اسکیمای مستقل در PostgreSQL (tenant_xxx)
  └─ مدیر شرکت                ← /app/<slug>
       ├─ اعضا و سطوح دسترسی   (نقش + **استثنای جز‌به‌جز برای هر نفر**)
       ├─ نقش‌ها و مجوزها       (RBAC، گروه‌بندی‌شده بر اساس پنل‌ها)
       ├─ زیرگروه‌ها، کارتابل و میز کار
       ├─ منابع انسانی         (تردد، تقویم، مرخصی و مأموریت)
       ├─ مالی — سیمرغ لجر     (کدینگ، سند دوطرفه، طرف‌حساب، گزارش‌ها)
       ├─ انبار                (انبارها، کالا، رسید/حواله/انتقال، کاردکس)
       ├─ HRC                  (ساعت هوشمند، پایش سلامت، نقشه، اعزام تیم)
       └─ یکپارچه‌سازی          (کلید API برای نرم‌افزارهای دیگر)
```

## پنل‌ها (ماژول‌ها)

هر شرکت فقط پنل‌هایی را می‌بیند که برایش فعال شده است. پنل خاموش نه‌تنها از
منو حذف می‌شود، بلکه مجوزهای آن از **دسترسی مؤثر** هر کاربر هم کنار گذاشته
می‌شود؛ یعنی حتی آدرس مستقیم هم کار نمی‌کند.

| پنل | کلید | چه چیزی می‌دهد |
|-----|------|----------------|
| سازمان و کارتابل | `org` | همیشه فعال — اعضا، نقش‌ها، زیرگروه، کارتابل، میز کار |
| منابع انسانی | `hr` | تردد، تقویم کاری، مرخصی و مأموریت، گزارش‌های حضور |
| مالی (سیمرغ لجر) | `finance` | کدینگ حساب، سند دوطرفه، طرف‌حساب، مرکز هزینه، سال مالی، تراز و معین |
| انبار | `inventory` | انبارها، کالا، رسید/حواله/انتقال/اصلاح، درخواست کالا، کاردکس |
| HRC | `hrc` | ساعت هوشمند، علائم حیاتی، موقعیت روی نقشه، هشدار و اعزام تیم |
| درگاه API | `api` | کلید API برای اتصال نرم‌افزارهای دیگر |

مثال: یک هولدینگ می‌تواند برای شرکت «تولید» فقط انبار + حضور و غیاب بخرد، برای
شرکت «بازرگانی» مالی + انبار، و برای شرکت «معدن» همه‌چیز به‌همراه HRC.

## سطح دسترسی جز‌به‌جز

سه لایه روی هم:

1. **پنل‌های شرکت** — چه چیزی اصلاً وجود دارد.
2. **نقش‌ها** — بسته‌های آمادهٔ مجوز (مدیر مالی، انباردار، کارشناس HRC…).
3. **استثنای هر نفر** (`member_permissions`) — دادن یا گرفتن **یک مجوز مشخص**
   برای **یک شخص مشخص**، بدون دست‌زدن به نقش‌ها.

فرمول دسترسی مؤثر:

```
(اجتماع مجوزهای نقش‌ها + استثناهای «بده» − استثناهای «بگیر») ∩ مجوزهای پنل‌های فعال
```

مسیر: **اعضا و دسترسی‌ها → دسترسی جز‌به‌جز این نفر**. برای جلوگیری از قفل‌شدن
شرکت، هیچ‌کس نمی‌تواند نقش یا استثناهای خودش را تغییر دهد.

## معماری

- **Next.js 14 (App Router) + TypeScript** — فول‌استک، RTL فارسی، Server Actions
- **PostgreSQL با اسکیمای جدا برای هر شرکت** (schema-per-tenant) — جداسازی کامل داده
- جداسازی امن با `SET LOCAL search_path` داخل تراکنش (سازگار با connection pool)
- احراز هویت با JWT در کوکی `httpOnly` (کتابخانهٔ `jose`)، رمزها با `bcrypt`
- کنترل دسترسی نقش‌محور (RBAC) با کاتالوگ مجوز در `src/lib/rbac.ts`

### کنترل‌پلین (اسکیمای `platform`)
- `companies` — هر شرکت = یک مستأجر، با `schema_name` اختصاصی
- `holdings` — هولدینگ مالکِ چند شرکت
- `user_accounts` — هویت سراسری (برای ورود و تشخیص شرکت)
- `companies.modules` و `holdings.modules` — پنل‌های فعال هر شرکت و پنل‌های
  مجاز هر هولدینگ (`text[]`)

### اسکیمای هر شرکت (`tenant_<slug>`)
- **سازمان**: `members`, `roles`, `role_permissions`, `member_roles`,
  `member_permissions`, `groups`, `member_groups`, `kartabls`, `kartabl_items`,
  `work_tasks`, `work_task_assignees`
- **منابع انسانی**: `work_schedules`, `holidays`, `schedule_overrides`,
  `attendance_days`, `attendance_punches`, `attendance_devices`,
  `face_embeddings`, `attendance_policy`, `member_employment`, `leave_*`
- **مالی**: `fiscal_years`, `ledger_accounts`, `ledger_entries`,
  `ledger_lines`, `parties`, `cost_centers`
- **انبار**: `warehouses`, `item_categories`, `items`, `stock_docs`,
  `stock_doc_lines`, `stock_requests`, `stock_request_lines` و نماهای
  `stock_moves` / `stock_levels`
- **HRC**: `hrc_devices`, `hrc_map`, `hrc_zones`, `hrc_readings`,
  `hrc_thresholds`, `hrc_alerts`, `hrc_teams`, `hrc_team_members`,
  `hrc_dispatches`
- **API**: `api_keys`

## راه‌اندازی محلی

```bash
# 1) دیتابیس
docker compose up -d

# 2) متغیرهای محیطی
cp .env.example .env
#   SESSION_SECRET را با خروجی  openssl rand -base64 48  جایگزین کنید

# 3) نصب و مقداردهی اولیه
npm install
npm run db:seed        # اسکیمای platform + ساخت سوپرادمین

# 4) اجرا
npm run dev            # http://localhost:3000
```

با ایمیل/رمز سوپرادمینِ تعریف‌شده در `.env` وارد شوید (`/login`)، سپس از
`/admin/companies/new` یک شرکت بسازید. مدیر آن شرکت می‌تواند با ایمیل/رمزی که
برایش تعیین کرده‌اید وارد `/app/<slug>` شود و کاربر، نقش، زیرگروه و کارتابل بسازد.

## زنجیرهٔ بازنشانی رمز عبور

هر کس رمز خودش را عوض می‌کند؛ اگر فراموش کرد، فقط سراغ **بالادستی خودش** می‌رود —
لازم نیست همه به یک نفر مراجعه کنند.

| نقش | رمز خودش | رمز چه کسانی را بازنشانی می‌کند |
|-----|----------|--------------------------------|
| هر کاربر شرکت | «پروفایل من» (با رمز فعلی) | — |
| مدیر شرکت | «پروفایل من» | اعضای شرکت خودش — «اعضا و دسترسی‌ها» |
| مدیر هولدینگ | `/holding/account` | کاربران شرکت‌های زیرمجموعهٔ خودش — «کاربران و بازنشانی رمز» |
| مدیر سیمرغ | `/admin/account` | مدیران هولدینگ و کاربران هر شرکت |

- **رمز پیش‌فرض `123456` است.** در فرم‌های ساخت شرکت/هولدینگ/عضو، فیلد رمز را
  خالی بگذارید تا همین رمز تنظیم شود؛ در بازنشانی هم فیلد خالی یعنی بازگشت به
  ۱۲۳۴۵۶. می‌توانید رمز دلخواه هم بنویسید.
- رمز بازنشانی‌شده **یک بار** با دکمهٔ کپی نمایش داده می‌شود و فقط هش bcrypt آن
  ذخیره می‌گردد.
- ورود هر حساب را می‌توان بدون حذف آن غیرفعال/فعال کرد.
- مرزها: مدیر هولدینگ فقط به شرکت‌های هولدینگ خودش دسترسی دارد، به حساب
  هولدینگ‌های دیگر یا مدیران هولدینگ دسترسی ندارد، و حساب سوپرادمین از هیچ‌کدام
  از این صفحه‌ها قابل ویرایش نیست.

### تغییر اجباری رمز در نخستین ورود

چون رمز پیش‌فرض ساده است، سامانه نمی‌گذارد کسی با آن کار کند:

- هر حسابی که رمزش را **مدیر تعیین کرده باشد** (ساخت حساب یا بازنشانی) علامت
  می‌خورد و در نخستین ورود مستقیم به صفحهٔ `/change-password` می‌رود.
- تا وقتی رمز شخصی انتخاب نشده، **هیچ صفحه‌ای از پنل‌ها باز نمی‌شود** — این
  قفل روی هر سه پنل (شرکت، هولدینگ، مدیر سیمرغ) برقرار است.
- رمز جدید نمی‌تواند دوباره ۱۲۳۴۵۶ باشد و رمز فعلی هم پرسیده می‌شود.
- حساب‌های قدیمی هم پوشش داده شده‌اند: هر کس با رمز `123456` وارد شود — حتی اگر
  از قبل علامت نخورده باشد — همان لحظه علامت می‌خورد و به تغییر رمز هدایت می‌شود.
- سرویس‌های JSON (فیدها، ICS، خروجی گزارش) قفل نمی‌شوند تا چیزی خراب نشود.

## دستورها
- `npm run dev` — اجرای توسعه
- `npm run build && npm start` — اجرای production
- `npm run db:seed` — مقداردهی اولیهٔ دیتابیس و سوپرادمین
- `npm run db:reset` — حذف کامل اسکیماها (احتیاط!)

## مالی و انبار در یک نگاه

- سند حسابداری ابتدا **پیش‌نویس** است؛ «قطعی‌کردن» مجوز جداگانه دارد و سند
  قطعی دیگر ویرایش نمی‌شود (فقط ابطال با ثبت علت).
- سند انبار هم پیش‌نویس ثبت می‌شود؛ **تأیید** آن موجودی را جابه‌جا می‌کند و
  اگر پنل مالی فعال باشد، **سند حسابداری قطعی** را هم خودکار صادر می‌کند
  (رسید: بدهکار موجودی کالا / بستانکار حساب‌های پرداختنی — حواله: بدهکار بهای
  تمام‌شده / بستانکار موجودی کالا).
- تأیید حواله‌ای که موجودی کافی ندارد رد می‌شود و کسری دقیقاً گزارش می‌شود.

## HRC — سلامت، ایمنی و اعزام

کارکنان ساعت هوشمند می‌گیرند؛ ساعت علائم حیاتی و موقعیت را می‌فرستد
(GPS، شبکهٔ مخابراتی/LBS، Wi-Fi، بیکن یا LoRa). سرور مقادیر را با آستانه‌های
شرکت می‌سنجد و در صورت لزوم هشدار می‌سازد: SOS، سقوط، ضربان بالا/پایین، افت
اکسیژن، تب، ورود/خروج از ناحیهٔ ژئوفنس، قطع ارتباط و باتری ضعیف. موقعیت هر نفر
روی **نقشهٔ شرکت** با رنگ وضعیت سلامت دیده می‌شود و تیم HRC با یک کلیک اعزام
می‌شود (اعزام → در مسیر → در محل → پایان)، با امکان **اعزام خودکار** در موارد
بحرانی.
