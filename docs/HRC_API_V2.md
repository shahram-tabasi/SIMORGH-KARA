# HRC نسخهٔ ۲ — راهنمای API (فاز ۳)

سرویس‌های سرورِ پلتفرم ایمنی. دو خانوادهٔ کاملاً جدا:

| خانواده | مسیر | احراز هویت | مصرف‌کننده |
|---|---|---|---|
| **دستگاه** | `/api/v1/hrc/*` | توکن دستگاه (Bearer) | اپ اندروید و ساعت |
| **اپراتور** | همان مسیرها، افعال دیگر | کوکی نشست مرورگر | مرکز فرماندهی و پنل وب |
| **یکپارچه‌سازی** | `/api/<slug>/v1/*` | کلید API | نرم‌افزارهای دیگر شرکت (بدون تغییر) |

شرکت از **توکن** پیدا می‌شود، نه از URL: دستگاهی که یک بار ثبت شد، نباید به
کد شرکت وابسته بماند که ممکن است عوض شود.

---

## ۱) قرارداد پاسخ

هر پاسخ، بدون استثنا:

```jsonc
{ "ok": true,  "data": { ... },                               "requestId": "…" }
{ "ok": false, "error": { "code": "…", "message": "…" },        "requestId": "…" }
```

`requestId` در هدر `x-request-id` هم برمی‌گردد و در لاگ سرور هست، پس گزارش
میدانی («ساعت ۱۴:۳۲ خطا داد») به یک درخواست مشخص وصل می‌شود. اگر هدر
`x-request-id` بفرستید، همان برمی‌گردد.

کدهای خطا: `bad_request` · `invalid_payload` · `unauthorized` · `forbidden`
· `device_revoked` · `member_inactive` · `not_found` · `rate_limited` · `internal`.

## ۲) هویت دستگاه

کلید خصوصی **هرگز** از Android Keystore بیرون نمی‌آید. سرور فقط کلید عمومی
دارد، پس حتی دزدیدن کل دیتابیس هم اجازهٔ جعل دستگاه نمی‌دهد.

```
۱) بلیت      کارمند در اپ: کد شرکت + ایمیل + رمز  →  بلیت ۱۰ دقیقه‌ای یک‌بارمصرف
۲) ثبت       اپ کلید می‌سازد → کلید عمومی + بلیت  →  توکن دستگاه ۳۰ روزه
۳) کار       هر درخواست با Bearer، و وضعیت ردیف دستگاه در همان لحظه چک می‌شود
۴) تازه‌سازی  چالش تصادفی سرور را با کلید Keystore امضا کن → توکن تازه
۵) ابطال     SUSPENDED/RETIRED یا بالابردن token_version → فوری، بدون انتظار انقضا
```

### `POST /auth/ticket`
```jsonc
// ← { "slug": "aahangari-demo", "email": "ali@…", "password": "…" }
// → { "ticket": "aahangari-demo.xK3…", "expiresAt": "…",
//     "company": {…}, "member": {…} }
```
به دسترسی `hrc.device.self` نیاز دارد. ایمیل اشتباه و رمز اشتباه **یک پیام
یکسان** می‌گیرند، تا این مسیر ابزار کشف کارمندان شرکت نشود.

### `POST /auth/enroll`
```jsonc
// ← { "ticket": "…", "device": {
//       "deviceUid": "…", "deviceType": "WEAR_OS_WATCH",
//       "publicKey": "<base64 SPKI DER>", "keyAlgorithm": "EC_P256",
//       "capabilities": { "heartRate": true, "fallDetection": true },
//       "gatewayDeviceUid": "<گوشیِ واسط، اختیاری>" } }
// → { "token": "<JWT ۳۰ روزه>", "deviceId": "…", "expiresInDays": 30 }
```
بلیت یک‌بارمصرف است. ثبت دوبارهٔ همان `deviceUid` (نصب مجدد اپ) ردیف را
به‌روز و `token_version` را یک واحد زیاد می‌کند — یعنی **توکن نصب قبلی
همان لحظه می‌میرد**.

### `POST /auth/challenge` → `POST /auth/refresh`
```jsonc
// ← { "slug": "…", "deviceUid": "…" }        → { "nonce": "…", "expiresAt": "…" }
// ← { "slug": "…", "deviceUid": "…", "nonce": "…", "signature": "<base64>" }
//                                            → { "token": "…" }
```
هر nonce یک‌بارمصرف است و **پیش از** بررسی امضا مصرف می‌شود، پس نه امضای
شنودشده دوباره کار می‌کند و نه می‌شود روی یک چالش امضا را حدس زد.
الگوریتم‌های پذیرفته: `EC_P256` (SHA256withECDSA) و `ED25519`.

## ۳) تله‌متری (توکن دستگاه)

همهٔ دسته‌ها حداکثر **۲۰۰** آیتم، و **جزئی‌موفق**: هر آیتم نتیجهٔ خودش را
می‌گیرد، پس یک رکورد خراب، ۱۹۹ تای دیگر را دور نمی‌ریزد.

| مسیر | کار |
|---|---|
| `POST /devices/heartbeat` | باتری، شبکه، مجوزها، اتصال ساعت به گوشی |
| `POST /location` | دستهٔ موقعیت‌ها |
| `POST /health` | دستهٔ سنجه‌های سلامت |
| `POST /events` | دستهٔ رویدادها (idempotent با `clientEventId`) |
| `POST /sos` | مسیر کوتاه و اختصاصی درخواست کمک |
| `GET /config` | ناحیه‌ها، فاصلهٔ ارسال، سیاست، اثرانگشت قوانین |
| `GET /status` | وضعیت ایمنیِ **خودِ همان کارمند** و بس |

### صداقت دربارهٔ کیفیت موقعیت

سرور خودش `quality` را تعیین می‌کند؛ دستگاه نمی‌تواند ادعا کند موقعیت
دکل مخابراتی دقیق است:

| منبع | کیفیت | سقف اطمینان |
|---|---|---|
| `GPS` | `ACTUAL` | ۰٫۹۰ |
| `UWB` | `ACTUAL` | ۰٫۸۵ |
| `WEARABLE` | `ACTUAL` | ۰٫۵۰ |
| `BLE_BEACON` | `ESTIMATED` | ۰٫۷۰ |
| `WIFI` | `ESTIMATED` | ۰٫۶۰ |
| `NETWORK` | `ESTIMATED` | ۰٫۴۵ |
| `MANUAL` | `ESTIMATED` | ۰٫۴۰ |
| `CELL` | `ESTIMATED` | ۰٫۳۰ |

اگر دستگاه اطمینان بالاتری اعلام کند، به سقف بریده می‌شود. رابط کاربری باید
`ESTIMATED` را دایرهٔ عدم‌قطعیت بکشد، نه سوزنِ دقیق.

### صداقت دربارهٔ شدت رویداد

دستگاه می‌تواند شدت را **پایین** بیاورد ولی هرگز بالاتر از سقفِ آن نوع رویداد
نبرد — وگرنه یک اپ معیوب می‌تواند مرکز فرماندهی را از CRITICAL پر کند.
مثلاً `LOW_BATTERY` که دستگاه آن را `CRITICAL` اعلام کند، `INFO` ثبت می‌شود.

### ضدتکرار

* **در سطح شبکه:** `clientEventId` یکتا به‌ازای هر دستگاه. صفِ آفلاین را
  هر چند بار بفرستید، یک رویداد ساخته می‌شود.
* **در سطح منطق:** تا وقتی یک رویدادِ همان **قانون** برای همان فرد باز است،
  دوباره ساخته نمی‌شود (۳۰ دقیقه؛ برای رویدادهای دستگاهی ۱۲۰ دقیقه).
  کلید این ضدتکرار **کدِ قانون** است نه نوع رویداد — چون همهٔ قوانین حیاتی
  `ABNORMAL_SENSOR_READING` می‌سازند و در غیر این صورت ضربان بالا می‌توانست
  نیم‌ساعت جلوی هشدارِ افت اکسیژن را بگیرد.

## ۴) دروازهٔ حریم خصوصی

`hrc_policies.monitoring_mode` جواب شرکت به «چه موقع اجازه دارید موقعیت من را
نگه دارید؟» است و **هنگام دریافت** اعمال می‌شود: موقعیتی که سیاست اجازه ندهد
اصلاً روی دیسک نوشته نمی‌شود، نه اینکه فقط در UI پنهان شود.

| حالت | یعنی |
|---|---|
| `SHIFT_ONLY` (پیش‌فرض) | فقط وقتی کارمند تردد ورود زده و هنوز خروج نزده |
| `FACILITY_ONLY` | فقط داخل محوطهٔ شرکت یا یکی از ناحیه‌ها |
| `ALWAYS` | همیشه — باید آگاهانه انتخاب شود |

پاسخ برای رکورد ردشده: `{"status":"skipped","reason":"outside_shift"}`.

**یک استثنا، عمدی:** `SOS` و `FALL_DETECTED` هرگز فیلتر نمی‌شوند. اگر کسی
بیرون از شیفت دکمهٔ کمک را بزند، شرکت باید بداند. اینجا ایمنی بر حالت پایش
مقدم است.

## ۵) موتور ریسک

قانون، **داده** است نه کد؛ در `hrc_rules` زندگی می‌کند و روی سرور اجرا می‌شود.
اپ اندروید فقط واقعیت گزارش می‌دهد؛ اینکه چه چیزی اورژانس است را شرکت تصمیم
می‌گیرد. یعنی مدیر ایمنی سیاست را عوض می‌کند بدون انتشار نسخهٔ جدید اپ، و دو
شرکت می‌توانند دربارهٔ «خیلی گرم» با هم اختلاف داشته باشند.

```jsonc
{
  "conditions": { "all": [
    { "fact": "heart_rate", "op": ">", "value": { "threshold": "hr_max" } }
  ]},
  "actions": { "event": "ABNORMAL_SENSOR_READING", "metric": "heart_rate",
               "message": "ضربان قلب بالاتر از حد مجاز — بررسی دستی توصیه می‌شود" }
}
```

* `value` می‌تواند عدد ثابت باشد یا به آستانهٔ همان شرکت اشاره کند.
* عملگرها: `> >= < <= = != in`.
* **واقعیتی که گزارش نشده، تخلف نیست.** سنسور خاموش نه «سالم» است نه
  «اورژانس» — جداگانه `SENSOR_UNAVAILABLE` ثبت می‌شود.
* قانون بدون شرط هرگز فعال نمی‌شود؛ `all` خالی یعنی «هیچ‌وقت»، نه «همیشه».
* پیام‌ها عمداً محافظه‌کارانه‌اند. این سامانه دستگاه پزشکی نیست و تشخیص نمی‌دهد.

پرونده حادثه (`hrc_incidents`) خودکار برای شدت `HIGH` و `CRITICAL` باز می‌شود.

## ۶) سرویس‌های اپراتور (کوکی نشست)

همان سه‌لایهٔ دسترسیِ بقیهٔ سامانه: پنل فعال → نقش‌ها → override جز‌به‌جز.
هیچ سیستم دسترسیِ دومی برای HRC وجود ندارد.

| مسیر | افعال | دسترسی لازم |
|---|---|---|
| `/incidents` | `GET` | `hrc.incidents.view` یا `hrc.monitor` یا `hrc.alerts.manage` |
| `/incidents/{id}` | `GET` `PATCH` | تأیید: `hrc.incidents.ack` · بستن: `hrc.incidents.respond` |
| `/incidents/{id}/responders` | `POST` | `hrc.dispatch` یا `hrc.incidents.respond` |
| `/incidents/{id}/responders/{aid}` | `PATCH` | همان |
| `/zones` `/zones/{id}` | `GET` `POST` `PATCH` `DELETE` | `hrc.zones.manage` یا `hrc.map.manage` |
| `/rules` `/rules/{id}` | `GET` `POST` `PATCH` `DELETE` | `hrc.rules.manage` |
| `/devices` `/devices/{id}` | `GET` `PATCH` | `hrc.devices.manage` |
| `/teams` | `GET` | `hrc.dispatch` یا `hrc.teams.manage` |
| `/policy` | `GET` `PATCH` | `hrc.policy.manage` |
| `/audit` | `GET` | `hrc.audit.view` |

### چرخهٔ عمر پرونده

```
OPEN → ACKNOWLEDGED → INVESTIGATING → RESOLVED → CLOSED
```
جلو رفتن از هر پله به هر پلهٔ بعدی مجاز است؛ **برگشت هرگز**. پروندهٔ بسته بسته
می‌ماند و مشکل تازه پروندهٔ تازه با شمارهٔ خودش می‌گیرد، تا تاریخچه بازنویسی
نشود. رویدادهای هر پرونده با آن حرکت می‌کنند و هر گذار با نام اقدام‌کننده در
`hrc_event_transitions` ثبت می‌شود.

اعزام تیم، پروندهٔ `OPEN`/`ACKNOWLEDGED` را خودکار به `INVESTIGATING` می‌برد:
تیمی که در راه است یعنی کسی دارد رسیدگی می‌کند.

چرخهٔ اعزام: `ASSIGNED → ENROUTE → ONSITE → DONE`، و `CANCELLED` از هر جای باز.

### قانون سیستمی حذف نمی‌شود

`DELETE` روی قانونی که `is_system` است فقط خاموشش می‌کند. حذف واقعی یعنی
مهاجرت بعدی دوباره می‌سازدش و مدیر ایمنی خیال می‌کند خاموشش کرده ولی نکرده.
ناحیه هم حذف نمی‌شود، غیرفعال می‌شود — رویدادهای گذشته به آن ارجاع دارند.

## ۷) حسابرسی و نگهداشت

هر کس به موقعیت یا سلامت کسی نگاه کند، رد می‌گذارد — **حتی خواندن فهرست
پرونده‌ها**. این همان چیزی است که پایش را قابل دفاع می‌کند: کارمند می‌تواند
بپرسد چه کسی، کِی، و چرا نگاه کرده، و جواب مستند بگیرد.

```
GET /api/v1/hrc/audit?member=<memberId>&limit=100
```

پاک‌سازی دوره‌ای:

```bash
npm run hrc:retention
# در cron، هر شب ساعت ۳:
# 0 3 * * *  cd /path/to/app && npm run hrc:retention >> /var/log/hrc-retention.log 2>&1
```

مدت نگهداشت هر نوع داده در `hrc_policies` تنظیم می‌شود (پیش‌فرض: موقعیت ۹۰
روز، سلامت ۱۸۰، رویداد ۳۶۵، ضربان دستگاه ۳۰). دو محافظ در این پاک‌سازی هست:

* آخرین موقعیتِ هر نفر هرگز حذف نمی‌شود، پس نقشهٔ زنده خالی نمی‌شود.
* رویدادِ **باز** هرگز حذف نمی‌شود، هر چقدر هم قدیمی — پرونده‌ای که هنوز
  رویش کار می‌شود، از زیر دست تیم کشیده نمی‌شود.

## ۸) نقش‌های آمادهٔ HRC

| نقش | کلیدها |
|---|---|
| کاربر (پایه) | `hrc.view`، `hrc.device.self` |
| نگهبان (HRC) | + `hrc.monitor`، `hrc.incidents.view`، `hrc.incidents.ack` |
| امدادگر (HRC) | + `hrc.incidents.respond`، `hrc.dispatch` |
| مدیر ایمنی (HRC) | + `hrc.zones.manage`، `hrc.rules.manage`، `hrc.devices.manage`، `hrc.analytics.view` |
| مدیر HRC | همهٔ کلیدهای پنل، شامل `hrc.policy.manage` و `hrc.audit.view` |

کلیدهای نسخهٔ ۱ همه سر جایشان‌اند، پس هیچ نقش موجودی دسترسی از دست نمی‌دهد.

## ۹) پیکربندی

| متغیر محیطی | کار |
|---|---|
| `SESSION_SECRET` | اجباری، حداقل ۳۲ نویسه. کلید توکن دستگاه از آن مشتق می‌شود (با جداسازی دامنه، پس توکن دستگاه هرگز به‌جای کوکی نشست کار نمی‌کند و برعکس). |
| `HRC_DEVICE_SECRET` | اختیاری. اگر بخواهید کلید توکن دستگاه کاملاً جدا باشد. |

هیچ کلیدی در کد نیست.
